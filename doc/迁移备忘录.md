# 公共地图模块与 RimWorld 1.7 迁移备忘录

本次目标是把 RimExodus 与 RimExodus: Delta-V 的底层地图能力提取到共同引用的 DLL，并适配 RimWorld 1.7。公共模块负责地图操作和引擎接线；两个 Mod 保留自己的地图关系、生命周期决策与玩法。本文保留迁移目标、调查依据与设计备忘。后续公共模块已迁入独立 RimExodus Framework 1.0.0，Delta-V 已移除实验开关并唯一使用 REF；当前实现状态、未完成项和验证结果见 [地图模块](地图模块.md)。本文保留原始调研时点，不表示所有规划能力均已完成。RimExodus 尚未接入。

核对日期：2026-10-29。范围为两个项目的当前源码工作副本，以及 `_references/RimWorldDecompiled_1.7`。该反编译的 `Assembly-CSharp` 标注程序集版本 `1.7.9781.31297`、目标框架 `.NETCoreApp,Version=v10.0`；后续施工须继续核对实际目标构建，不能仅以“1.7”代替精确基线。

## 1 结论与现状差异

1. **以 Delta-V 的自研 prefab 序列化为统一内容保存机制的基础，纳入现有整图归档的状态保真能力，并提取无 tile 口袋图；以 RimExodus 的降频与原版跨图射击为补充。** 当前类仍有玩法依赖，需要拆出明确的回调与策略入口，不能只改 namespace 后打包。
2. **完整原版多图渲染是新增能力。** RimExodus 当前只重放指定静态层和部分动态物，Delta-V 当前重放船壳；两者都不是“任意角度下完整调用原版地图绘制”的成品。
3. **1.7 渲染后端必须先做原型验证。** 旧 Unity `CommandBuffer` 的提交和清深度在该参考版本中是告警桩；简单换成 `Graphics.DrawMesh` 不能自动保留 Delta-V 的整壳遮挡顺序。
4. **区域模板、区域封存与 prefab 制作统一为“区域选择 → 内容序列化 → 按需重建”，整图归档是选择范围覆盖全图的特例。** 居住区只是最常用的区域标记方式之一，必须允许其他标记方式接入。RimExodus 现有 `ZoneMapRecord` 将迁到这套 prefab 机制。克隆与原样恢复的身份处理、源图是否卸载等属于同一机制的操作选项，不据此拆成独立保存系统。
5. **显示、模拟和战斗许可分开。** 一张地图可以可见但不模拟，也可以正在卸载而禁止交战；不能用 `Find.Maps.Contains`、是否被绘制或一个 `active` 布尔值代替全部判断。

源码入口及 1.7 定位见第 10 节；以下“需新增”“建议契约”“待验证”均为后续施工事项。

## 3 多地图渲染与坐标契约

### 3.1 原版绘制模式的范围

1.7 `Map.MapUpdate` 不只是画图：它还更新电网、房间、光照、Lord 和组件；真正的绘制段受 `Find.CurrentMap == this` 限制。`MapDrawer` 和 `DynamicDrawManager` 的裁剪又读取当前相机视区。因此不能为每张邻图直接再调用一次 `MapUpdate`，也不能通过反复设置 `Game.CurrentMap` 来模拟多图绘制；后者会触发两个 Mod 的聚焦、唤醒及相机副作用。[V2、V3]

新增默认模式应尽量复用原版各层的生成和绘制入口，并补齐以下范围，而不是把 RimExodus 的四层白名单改名为“原版模式”：

- 全局 `MapDrawLayer`、section 各层，包括地形、建筑、屋顶、雪/沙、光照、雾及 DLC 层；保留第三方层的可接入性。
- Pawn 的初始化、预绘制、正式绘制及剪影，普通 realtime Thing、Projectile、Mote、Fleck、临时 Thing、地图效果。
- 水面颜色层与 `WaterDepth` 深度层配对，地图边缘裁剪的取舍，区域/指定/选中等 UI 叠层的显式开关。
- 原版雾中隐藏、雪/沙深度、离屏绘制和阴影判据；多图绘制不能泄露尚未探索的动态物。

将“需要执行的显示维护”“每游戏 tick 模拟”“实际绘制提交”拆开调度。对 0 tick 的可见图，可维护脏网格和渲染缓存，但不能借绘制推进 Pawn、天气计时或游戏组件模拟。第三方 `MapComponentUpdate/Draw` 是否依赖 CurrentMap，要按具体入口验证，不能承诺自动兼容全部 Mod。

### 3.2 自定义模式应复用同一管线

建议把能力拆成绘制计划、内容收集、提交后端三个职责；完整原版模式和自定义模式共用裁剪、坐标、缓存失效及提交，不建立两套全局捕获补丁。

RimExodus 当前的光照处理更准确地说是：保留邻图灯光与屋顶顶点数据，把邻图光照材质 alpha 设为 0 来去掉重复天色染色，再统一补天色；并不是完全不读取真实光照。其静态层为 Terrain、ThingsGeneral、LightingOverlay、FogOfWar，另提交 Watergen；动态物单独绘制，未重复运行完整邻图 Fleck 绘制。[R1]

Delta-V 的默认船壳只保留特定地形及建筑，动态捕获复用原版 Thing 绘制，另有门开关终态、炮塔顶部和壳面分层规则。`ShellRenderRuleDef`、船体筛选和太阳方向算法应留在 Delta-V；通用层只提供过滤、替换、命令收集和稳定排序。`MapOverlayRenderer` 内直接使用 Delta-V Comp/Def 的分支不能整体搬入公共 DLL。[D1]

### 3.3 1.7 渲染迁移重点

| 已核实事实 | 迁移动作 |
| --- | --- |
| `Camera.AddCommandBuffer`、`CommandBuffer.DrawMesh/Clear/ClearRenderTarget` 是告警桩 | 1.7 使用实际可工作的提交路径；不能以 API 仍存在或能编译为验收依据 |
| RimExodus 通过 `CommandBuffer` 所属程序集名识别 `UnityStubs`，改走 `Graphics.DrawMesh` | 可借用运行时分支和主图层/WaterDepth 分流；1.7 专用库不必照抄全部 1.6 支路 |
| RimExodus 即时路径用邻图高度减 0.01 缓解重叠 | 这是其地表重叠带方案，不等价于 Delta-V 的逐壳、逐表面清深度，不能直接套用 |
| `ShellLayer` 当前固定构造 `CommandBufferShellDrawBackend` | 应改为公共后端选择；先验证整壳排序、透明层和前景效果，再切换消费者 |
| Delta-V 捕获 12 参数 `Graphics.DrawMesh` 重载；1.7 常用 4/7 参数调用直接走其他重载和 `Internal_DrawMesh/DrawMeshCore` | 旧捕获可能绑定成功却漏掉实际绘制。核对真实调用链，覆盖 `MaterialPropertyBlock`、`DrawPropertyBlock`、Waylith Material 等相关出口，避免多层重复捕获 |
| `MapRenderFeature.CaptureFrame` 收集统一提交快照，读取全局 shader 状态、太阳方向及当前图背景色 | 临时改一遍源图全局 shader 再恢复，不保证每条命令保留该图环境。完整模式的多图光照/水纹/阴影要验证每图参数或 pass 隔离；不能先承诺完全一致 |
| `CaptureFrame` 在 `mapBeingGenerated != null` 时关闭地图 pass | 将 RimExodus 的生成期渲染门补丁纳入公共生成服务，只放行“公共服务生成另一张图、当前图已完成”的情况，不修改真实 static 值 |

源码依据：[V1、V2、V3、R1、R2、D1]。RimExodus 已有适配代码及局部实测注记，可以作为起点；这不构成 Delta-V 任意旋转船壳已通过 1.7 验证的证据。

渲染后端原型的优先验收场景：两张半透明地图重叠、三壳交叠、任意角旋转、水面邻接、昼夜/室内灯光、放大缩小与快速平移、聚焦切换、后台生成和地图删除。不得用全图每帧 `RegenerateAllLayers` 或复制整套材质来回避正确性问题。

### 3.4 坐标与拾取

建议公开显式 `sourceMap → destinationMap` 的转换上下文。平面刚体绘制满足 `pDestination = M × pSource`，方向不加平移；需要旋转中心时由调用方提供完整矩阵或中心与姿态，模块不猜地图左下角或几何中心。当前聚焦图必须 identity。

- RimExodus 适配器保持 `neighborLocal + offset = hostLocal`，仅开放原有合法邻接域；worldtile 和多边形接缝不进入公共坐标类型。
- Delta-V 的 `SpaceTransform/OrbitSphere` 继续是球面位置、速度与物理唯一权威。公共接口接受它提供的显示矩阵和精确转换；不能在 DLL 内复制第二套球面坐标。
- 区分**显示用刚体矩阵**与**权威逻辑点转换**。Delta-V 当前船壳是刚体显示，任意球面点互映射则经过球面运算；不能承诺远距离球面转换都严格等于同一个平面矩阵。拾取按被绘制实例的逆矩阵回到源图，逻辑轨道查询仍走 `SpaceTransform`，两者不能相互冒充。
- `Vector3` 连续点与 `IntVec3` 格子分开；明确格角、格心 `+0.5`、负坐标向下取整、角度手性与 Rot4 约定。任意角变换不能把格子直接四舍五入后反复往返。
- 每帧显示计划冻结源图、变换和层序，裁剪、命中拾取及选中反馈使用同一份快照；模拟时按游戏 tick 使用权威姿态。图替换或租约变化后，旧计划失效。
- 视区逆变换后取保守包围范围，再做源图/section 裁剪；不要只减 offset。拾取先按视觉层序逆序检查，再返回 `(Map, localPoint/cell, Thing)`；不要只返回裸格。
- 目标高亮、射程圈、命令预览、鼠标坐标及空间音源需要同一转换入口。相机缩放、切图、是否允许邻图选择/下令由调用方决定，渲染能力本身不授权跨图寻路。

## 4 无 tile 地图与公共宿主

Delta-V 已有较小的可提取入口：`IPocketMapHostProvider`、`PocketMapHostService`。该服务通过原版 `GenerateMap(..., isPocketMap:true)` 创建地图，把 parent 加入 `Find.World.pocketMaps`，从现有 pocket parents 找回宿主；缓存不作为持久事实。[D2]

1.7 的 `PocketMapUtility.GeneratePocketMap` 仍采用同样的注册路径，`PocketMapParent` 仍保存 `sourceMap` 和 `mapGenerator`。`Map.TileInfo` 在 pocket 模式读独立 `pocketTileInfo`，因此无实际 worldtile 的地图不是伪造一个轨道 tile。[V5]

迁移要求：

- 保留 `Tile = PlanetTile.Invalid`、只登记 pocketMaps、独立 `pocketTileInfo`，以及 sourceMap 宿主不聚焦、不作为普通事件目标、默认 0 tick 的规则。宿主不能成为坐标原点或承载船体事实。
- parent 创建、宿主识别和 generator 作为输入；`ShipPocketParent_DeltaV.EnvironmentalTile/WorldCameraPosition` 保留在 Delta-V 或其适配器。通用层不依赖轨道层、星区或 `SpaceObject`。
- 统一注册、失败清理及读档重绑，保证 child parent 的 sourceMap 引用有效。若支持多个消费者共享宿主，必须明确 child 登记和宿主释放条件，不能由一个消费者重置时删除另一个消费者的宿主。
- 1.7 `StorytellerUtility.DefaultThreatPointsNow` 仍把 pocket 图目标改为 `sourceMap`；空宿主的财富和事件语义不等于普通基地。事件路由应有调用方政策，不能只靠“有个 sourceMap”就声明 storyteller 已正确。
- `Game.DeinitAndRemoveMap` 仍会按 `destroyOnParentMapAbandoned` 级联处理子口袋图。删除、归档、宿主重建必须分别定义；尚有子图/归档引用时不能随意销毁宿主。
- 不沿用旧注释作为 1.7 崩溃结论：该版本 `WorldObjectsHolder.Add` 对无效 Tile 的检查明确豁免 `PocketMapParent`。继续采用原版 pocket 注册链是契约选择，并不据此断言所有进入 WorldObjects 的 pocket parent 必然在同一位置崩溃。

## 5 统一区域 prefab 序列化与按需重建

### 5.1 统一机制与区域选择接口

区域模板、区域封存、prefab 制作和整图归档共用一套内容模型、捕获入口与重建管线。RimExodus 的居住区重建也迁入这套机制，不继续维护独立的简要属性记录和回放实现。

区域选择接口显式接收源 Map，由调用方提供区域标记或格集合，捕获开始时解析并冻结为本次 mask。Home Area 是一个内置适配；其他 Area、自定义标记和调用方生成的格集合使用同一接口。全图选择直接返回该 Map 的全部格，不要求先把整图涂成居住区。保存记录保留实际 mask，包括无内容格和孔洞，恢复不重新读取可能已经变化的标记。

同一机制通过操作选项表达具体用途：

| 维度 | 契约 |
| --- | --- |
| 选择范围 | 居住区、其他标记或任意格集合；全图是范围特例 |
| 内容范围 | 按用途声明要保存的内容层与持久状态；全图归档覆盖全部可保存内容及地图级状态，不能受当前 Building/Item 导出过滤限制 |
| 重建身份 | 制作可重复使用的模板时克隆并分配新身份；恢复封存内容时按恢复契约保留身份及引用；派系和 marker 展开同样显式选择 |
| 放置与源图处置 | 盖章或区域置换；保存成功后保留源图、移除所选内容或卸载整图，由对应操作编排并验证 |

这些是同一机制的参数和生命周期差异，不建立各自的序列化实现。先统一现有 prefab 与整图归档可复用的捕获、引用和重建能力，再让各调用入口选择所需行为。

### 5.2 采用 Delta-V 自研序列化核心

`MapPrefab.Export` 以 Home Area 或任意 cell mask 捕获，建筑/物品逐实例保存 `Thing.ExposeData`；地形使用原版 Prefab 格式，foundation 和 roof 单独保存。`MapPrefabThingState.Instantiate` 把全部实例放进一次 Scribe 加载，先解析旧 ID 对应的内部引用，再给本次克隆的所有深读 Thing 重分配 ID，并重算 `VerbTracker` 内的 Verb 身份。这正是公共区域保存应保留的核心，不引入额外基架管理框架。[D3]

“不受外部基架框架管理”不等于丢弃原版 foundation 层；原版地形/屋顶保存是地图内容能力，Delta-V 的 `SubstructureOwnership`、驾驶台和舰船归属才是消费者策略。

需拆掉的具体耦合：

| 当前耦合 | 提取方式 |
| --- | --- |
| `Export` 读 `Find.CurrentMap`；输出目录来自 Delta-V | 公共 API 显式接收 Map、掩码及路径/流；文件扫描和生成池留消费者 |
| 原版 `PrefabUtility.CreatePrefab` 本身也读 `Find.CurrentMap` | 单改 Export 参数不够。非聚焦图捕获须另行适配地形采集入口或建立受控上下文；不得设置真实 CurrentMap 触发聚焦 |
| 实例排序引用武器挂件与主驾驶台 | 通用放置依赖顺序 + 消费者排序扩展，默认只理解原版依赖 |
| `Spawn` 参数含 `ownerId`、`UniverseManager`；直接认领基架 | 把归属认领、身份重置放进 Delta-V 前后置处理 |
| 导弹仓特殊类型回退、弹药入仓、炮塔旋转、对接口局部状态重定位 | Delta-V 内容适配器负责；公共模块只提供本次 root/Rot4、实例映射和落位结果 |
| `CompPrefabMarker.Expand` 生成船员及装备 | 注册显式实例化后处理；整图恢复不得触发 marker 再展开 |

当前导出只纳入**锚点格在掩码内的顶层 Building/Item**，不把地图 Pawn、Filth、Blueprint 等当模板条目；嵌套持有内容仍可能随 Thing 的 Scribe 被读写，不能笼统保证“模板绝无 Pawn”。容器内容的纳入/排除必须形成明确政策和验证用例。

当前导出/导入允许失败条目退回默认状态或跳过，并输出 warning；`Spawn` 数量不符也只是告警。公共接口必须返回丢失、降级、冲突的结构化结果。可重复生成模板可以显式允许降级；承担玩家区域保存时，默认不能把降级结果当作成功后删除源图。

### 5.3 RimExodus 区域封存迁入统一机制

`ZoneMapRecord` 保存原始 Home 格集合，建筑按占用格相交收集并去重，而 Delta-V prefab 按锚点格纳入。它只保存建筑简要属性、地板/基架、屋顶及物品，不保完整 Comp，也不保地图 Pawn。`ArchiveTileMap` 记录后调用 `DeinitAndRemoveMap`；恢复由 `GenStep_ZoneRestore` 在生成链中置换区域、恢复 Home，外围继续自然生成。[R4]

以上是现有实现的迁移起点。后续替换为公共 prefab 的区域序列化与按需重建，外围自然生成和生成后区域置换由 RimExodus 编排。接入时还要补充：

- **原始区域 mask 的持久化。** 当前 `MapPrefabDocument` 只有包围尺寸和内容列表，没有完整选择掩码；内容为空的格、掩码孔洞不能从列表反推。Home 及其他标记适配均使用第 5.1 节的共同选择接口。
- **区域置换模式。** 模板盖章与“空白也有权威含义”的区域恢复不同。明确清障边界、多格建筑跨边缘、不可拆关键物、物品推移、基础自然地形回填和 Home 恢复。
- **派系与身份政策。** 可复制模板统一目标派系并清外部旧引用；区域封存是否保留原派系/外部身份按其业务契约处理，不能无条件套模板重编号与清空规则。
- **原生成顺序。** 当前 ZoneRestore 为 order 1100；不要照抄 `ZoneMapRecord` 残留的旧 395 注释。1.7 接入时还须核对目标版本 XML 的实际 GenStep 顺序，本文只核对了源码及现有项目声明。
- RimExodus 已发布，现有 `preserveRecord` 与序列化类迁移涉及旧档。保留旧读取适配还是宣布破坏兼容，在执行该变更前由用户决定；Delta-V 不为旧开发快照新增迁移体系。

统一机制必须在捕获和重建请求中明确克隆或恢复意图；身份处理不能由“区域/整图”推断。Scribe、内容记录、引用处理、压缩/IO、验证和重建共用实现，按选项执行新身份分配或身份保留。

## 6 全图范围的归档与恢复

### 6.1 将 ArchivedMapStore 的保真能力纳入统一 prefab 机制

整图归档使用第 5 节的同一内容保存与重建机制，选择范围覆盖全图，配套整张 Map 的卸载和重新加载。需要保存 Pawn、容器、区域/分区、地图组件及其他持久状态；仅把当前 prefab 的 Building/Item 掩码扩大到全图尚不能满足这一要求。

现有 `ArchivedMapStore` 流程是 `Map.ExposeData → XML 核心节点检查 → GZip/Base64`；卸载保留地图内容身份，移出 `Game.maps` 并处理 tick、signal、声音、后续地图索引与资源释放；恢复进入 `ProgramState.MapInitializing`，Scribe 深读 Map，登记外部引用，`Game.AddMap`，完成 Scribe 引用解析，再调用 `Map.FinalizeLoading`。这些原版状态读写和生命周期处理应纳入统一管线，不将现有整图 XML 包装器原样确立为另一套公共保存系统。[D4]

`TryRestore` 目前限定 `PocketMapParent expectedParent`，所以尚不是表面图通用归档 API。提取时需支持一般 `MapParent`，把世界 parent / pocket parent 的登记与引用提供方式分开；保留 Map uniqueID、Thing ID 与 parent 关系，不能保留会变化的 `Map.Index` 作为身份。

1.7 `MapDeiniter.Deinit` 仍会把 Pawn 交给世界池、通知区域与 Lord 移除、清 Thing 列表；它适合真正删除，不适合整图原样恢复。公共模块必须明确区分 `ArchiveUnload` 与 `DestroyMap`，不能把二者接成同一个“删图”实现。[V4]

### 6.2 必须补齐的事务与引用边界

1. **先预检和捕获，再卸载，最后发布归档表示。** 源图可保存 Thing ID 无效/重复时拒绝；归档数据未完整生成前不动原图。恢复通过身份、内容及注册验证后才移除归档记录。
2. **同一时间只允许一个 Scribe 操作。** 普通保存、区域实例化、归档和恢复共用互斥；Scribe 活动期间不排入跨帧延续。ProgramState 和加载上下文必须用 finally 恢复。
3. **不要把“不抛异常”当保真。** 1.7 `Map.ExposeData` 可捕获单个 Thing 保存错误；`Map.FinalizeLoading` 也逐个捕获落位错误。当前只验证 mapInfo/things 节点、ID 和 Pawn needs 还不足以证明完整保真。应核对持久实例清单、关键组件与嵌套引用，明确排除本就不保存的 Mote 等瞬态内容。
4. **双向外部引用。** 当前登记 factions、ideos、quests、world objects、pocket parents、world pawns 和其他加载图的对象，主要解决“归档内容引用活对象”。活对象指向已归档 Thing、两张归档图互相引用、第三方全局注册表，不因这份登记自动解决。未覆盖关系应阻止卸载或通过明确的引用提供/重绑机制处理，不声称已经无损。
5. **当前 `CanUnloadLosslessly` 是有限预检。** 它检查异常石柱、排队事件及活跃任务的 Look/Select targets，并未遍历所有 QuestPart 或第三方状态。公共层应允许调用方追加阻止理由；恢复失败保留归档，不能创建一个相似的新图替代。
6. **跨图表索引与资源必须一起清理。** 归档处于 maps 中间的图时，后续 Thing/Region/District 索引及 currentMapIndex 要一致；同时清理公共渲染、查询、音效、战斗目标与消费者缓存。当前归档自行卸图，不能只依赖 `DeinitAndRemoveMap` 补丁收到通知。
7. **加载收尾仍需验证。** 1.7 `FinalizeInit` 重建 pathing、region/room、电网、温度真空缓存、水体等；`Dispose` 释放 PathFinder、多个网格及 mapDrawer。资源释放是原版路径的一部分，不能移出 maps 后只停 tick 就结束。
8. **归档期外部行为由消费者管理。** Delta-V 保存 objectId、位姿和无法从卸载图重建的动力摘要，仍按 universe tick 漂移/导航；RimExodus 决定地图滚动及恢复。公共 DLL 不模拟无图船舰，也不决定维修或敌舰退场。

归档记录必须随正常游戏存档持久化；渲染缓存、调度集合和中途事务不持久化。库命名、类型搬迁和记录位置要在首次接入前固定，避免两个消费者分别存一份相同归档。

## 7 tick 速率与休眠

### 7.1 提取内容与语义

底层必须同时处理 `MapPreTick`、`MapPostTick` 和全局 `TickList → Thing.DoTick`。只跳 Map tick 不会停建筑与 Pawn。0 速率应摘除不运行的 Thing，恢复前先 `RemoveAllFromMap`，再仅注册 `thing.Map == map` 且有效的实例，避免双 tick 和陈旧 spawnedThings 条目。RimExodus 已有这个过滤；Delta-V 当前 Wake 仅检查 Spawned/Destroyed，提取时应合并较严格的条件。[D5、R3、V6]

公共速率服务按 Game 实例持有状态，不照搬 RimExodus 的可变静态字典；两个 Mod 的距离/威胁政策仍各自决定请求。未登记地图直接走原版。每图由明确 owner 管理，冲突请求应报出，不让补丁加载顺序决定最终速度。

建议首版契约为 `0..1` 的执行比例，不承诺大于 1 的加速。保留已有离散档或提供准确的比例调度需在 API 中说清：RimExodus 当前 `ceil(100 / percent)` 会把 75% 变为每两次执行一次，实际是 50%，不能把它标成精确百分比。

休眠可定义为**速率 0 + 无全速例外**；是否继续显示、执行必要显示维护、允许事件或自动唤醒分别配置。RimExodus 当前“0% 凝固”还允许接缝快速区全速，因此不能直接等同于严格全图休眠；快速区应成为由调用方提供的可选例外策略。

### 7.2 已发现的迁移检查项

- **Pre/Thing/Post 相位错位：** 1.7 `DoSingleTick` 顺序为 `MapPreTick → ticksGameInt++ → 三个 TickList → … → MapPostTick`。RimExodus 当前 Pre/Post 共同调用 `(TicksGame + mapId) % N`，Normal Thing 也读即时 TicksGame。对 N=2，同一轮 Pre 可能跳过而 Thing/Post 放行。提取前必须以同一逻辑轮次冻结决策或明确换算 upcoming tick，再测试三阶段同步，不能依赖注释中的“同拍”。
- **Rare/Long 混叠：** 原版桶间隔仍为 250/2000。应按该 Thing 的有效调度机会计数/相位，不能直接套 Normal 的全局 tick 取模；RimExodus 已处理这一问题，需保留相关回归。
- **降频不是等价加速补偿：** 1.7 `Thing.DoTick` 仅在实际执行时增加 `tickDelta`。被跳过的调用不会自动计入下一次 `TickInterval(delta)`；按 `TicksGame` 差值计算与逐 tick 累加的系统行为不同。不能笼统说需求、电量和冷却都保持原速。
- **Pawn 移动补偿是专门政策：** RimExodus 乘 `CostToPayThisTick` 以恢复平均移动速度，不能推导所有 AI/战斗/组件都安全。严格冻结不补时，重新唤醒不默认重演整段历史。
- **新增和跨图 Thing：** 冻结后 Spawn、传入、物品容器展开以及由引擎重新注册的 Thing 仍需被门禁接管；只在入睡时摘一次表不构成完整 0 tick。
- **MapUpdate 独立：** 不能按游戏 tick 的取模结果跳显示帧。完全休眠可停止其模拟性 Update；可见冻结图按第 3 节维护显示。
- **图外系统：** Storyteller、Quest、WorldObject 和其他 Mod 的 GameComponent 不都经过地图门禁。事件目标过滤与调用方配合必须列出，不能承诺 0 tick 会冻结整个世界对该图的一切影响。

交战域中的射手、目标和原版飞行弹体建议请求全速执行，并阻止相关地图归档；解除条件由战斗服务管理。Delta-V 的宇宙物理和 `SpaceProjectile` 不跟随内部 Map 的降频，仍遵守每游戏 tick 一次积分。

## 8 可开关跨地图战斗

### 8.1 从 RimExodus 提取可复用部分

现有基础涵盖 `SeamlessCombatCoords`、`SeamlessCrossMapSight`、纯格目标侧表、索敌/Targeter/ShootLine/ShotReport、原版 Projectile 越缝交接，以及独立的 CE 兼容层。开关已有 `crossMapCombatEnabled`，但许可绑定 Surface 邻接、整数 offset、多边形归属与休眠过滤，不能原样覆盖旋转中的宇宙地图。[R5]

建议以调用方登记的战斗域为最小边界：源图、目标图、有效期/表示代次、转换与射线归属查询、可交战许可。显示域不自动成为战斗域；开关按域或消费者控制，不用一个全局设置同时打开两个 Mod 的所有地图。

公共能力至少包含：

- 原版 Pawn/炮塔的跨图候选、敌我过滤、射程与最小射程、LOS、掩体、射击报告、朝向及玩家目标高亮。
- `(Map, Thing/Cell)` 目标；纯格目标没有自带 Map，必须持有真实目标图上下文，不能塞假 Thing 或依赖 CurrentMap 推断。
- 原版投射物起点/终点、miss 分支和剩余飞行状态在明确坐标系中转换；在越界/拦截/命中前交接，目标图原生结算伤害与爆炸。
- 不应把近战追击、跨图 Job、预约和跨缝寻路隐含在“开启战斗”里；这些需要独立移动许可，Delta-V 不因此新增跨图 live 行走。
- 同图和未登记图完全回落原版。CE 的移动弹、instant ray、能力和炮塔按可选适配器接入，未安装零行为；RimExodus 已有 CE 支持不等于已核实 CE 的 1.7 版本兼容。

1.7 原版 `Verb.TryFindShootLineFromTo`、`Verb_LaunchProjectile.TryCastShot` 和 `Projectile.CanHit` 仍检查图一致性，显示一张邻图不会使它自然可攻击。`Projectile` 仍有 origin/destination、ticksToImpact/lifetime 与 `TickInterval(int delta)`，相关 patch 必须逐个重核重载、参数名和实际 IL。[V7]

### 8.2 不能直接沿用的几何假设

RimExodus 的 Projectile 实现按平移交接，两端坐标一起加减 offset，依赖凸接缝区域；其 Launch 对某些 miss 坐标系采用“离目标哪种表示更近”的判别。这依赖邻图间距远大于 miss 半径。公共实现应显式记录坐标系，不能把距离猜测推广到重叠、旋转、移动地图。

现实现也记录了“高速越缝步可能跳过源图侧拦截”的边界。通用射线需按各地图的真实几何分段，在任意旋转/重叠下确定沿射线最先遇到的实体；不能靠屏幕层序选命中地图，也不能假设两个端点在同图就绝无中途穿过另一图。爆炸默认在实际命中 Map 内原生结算；跨图 AoE 是另外的扩展，不能隐式重复爆炸。

Delta-V 已有 `SpaceProjectile → SpaceCollision → 目标 Map 后效` 权威链。公共层提供目标转换/查询和原版伤害交回入口，不能在 DLL 中再跑一条宇宙弹道或把弹体按 Map 边界切换坐标。Delta-V 要不要让普通 Pawn/原版枪械进入该宇宙链，是后续具体接入决定，不能在提取时默认启用第二套伤害。

### 8.3 开关、休眠与保存

必须定义关闭瞬间的在途状态。建议：关闭后禁止新索敌/施法/发射，清理未执行命令；已获准发射的弹体保留完成本次飞行所需上下文与地图保活，直至命中或正常消失，再释放。不能在弹体已使用统一坐标后直接让迁移 Prefix 失效，导致它突然按原图坐标结算。这个建议需在实现时与两个 Mod 现有开关行为统一。

飞行期间切图不改变弹道；目标图卸载、替换、销毁或目标跨图时按真实身份重新校验，失效目标不自动落到同坐标的另一图。原版持久弹体的跨图上下文需要可重建或随正常存档保存；RimExodus 当前 `ConditionalWeakTable` 标记不持久化，不能把进程内已标记当读档后仍成立。Delta-V 的宇宙瞬态弹体仍沿用自己的保存政策。

## 9 提取结构与实施顺序

### 9.1 一个实现与明确的消费者边界

建议以一个独立公共项目、一个运行时 DLL 为初始交付，不预先拆成大量包。内部按 Render、Coordinates、PocketMaps、Serialization、Lifecycle、Scheduling、Combat、Generation 分域即可，名称待建项时确定。

引用方向固定为 `RimExodus → 公共 DLL ← Delta-V`。公共项目只引用所需的 1.7 引擎类型、Harmony 及实际用到的运行时 API，不反向引用任一 Mod，也不默认新增 VEF/KSCG/CE 等硬依赖。公共实例服务挂到当前 Game；玩法状态继续留各自 manager。

公共接口最少要表达：地图登记与 owner、地图表示代次、绘制/坐标 provider、每图速率和例外、可扩展区域选择与统一 prefab 捕获/重建请求及结果、包括全图卸载在内的封存事务、生成请求、战斗域许可、帧安全动作及消费者清理通知。优先从现有方法签名去掉具体 Mod 类型，不为未来兼容新增通用消息总线或第二套世界管理器。

DLL 应只有一个部署/加载来源。建议独立依赖 Mod 承载公共 DLL，两个消费者引用同一产物并声明依赖，避免各自在 Assemblies 携带同名不同版本副本。若最后选择其他打包方式，也必须验证程序集身份、类型单一性和 PatchAll 只执行一次。

同一底层入口统一拥有者后，移除消费者旧补丁接线；不要让两个 Prefix 各自跳 tick、两个 CurrentMap 补丁各自唤醒、两个渲染门补丁各自解释后台生成。切换以能力为单位完成，避免长期并行维护两份等价实现。

### 9.2 一并统一的生成、转移和资源管理

- 两个增量生成器都占用 `MapGenerator` static、Rand 与生成工作数据。公共服务必须互斥所有消费者及已支持的 MapPreview 预览；“每个 Mod 内各只有一个任务”仍可能同时生成。外部同步生成保留同步返回约定，不能全局异步化。
- 保留 `Prepare → GenStep → FinalizeInit/MapGenerated/parent.PostMapGenerate → PostMapInitialized → 成功发布` 顺序和失败收尾。第三方 Postfix 复放只对绕过原方法本体的成功增量路径执行一次；不能单独复放 Prefix/transpiler/finalizer。
- 帧预算暂停时可继续推进生成，但不能以帧时间推进物理。统一半成品图的 tick/渲染/保存门禁，退出/删图/取消都释放生成锁；1.7 渲染门补丁使用同一生成状态。
- 区域搬运保留 `CaptureDomain → StripDomain → PlaceIntoMap`，复核 1.7 Gravship 私有字段及原版放置收尾。Prefab 克隆不是搬运：真实搬运不重分配 Pawn/Thing 身份。抽出通用搬运后，由 Delta-V 适配器处理归属、对接口与速度继承。
- RimExodus 跨缝 Pawn 转移及外部载具/骑乘关联是另一种业务模式；可以复用清理与原版 Spawn/DeSpawn 接线，但不把其传送许可和路径桥接强加给 Delta-V。
- 图池按通用类别键、尺寸及生成契约租用，不把 `SpaceObjectTag` 写入公共 API；保留租约身份和旧回调拒绝、非空归还拒绝、部分填充失败保留内容、换档重建与删除释放。原版单格图生成的特殊修复须重新核对 1.7，不能无证据永久保留。
- 帧安全队列共享一个实际执行点，Delta-V 原 `QueueFrameAction` 可成为转发入口；动作校验地图/表示代次/租约。不得把 `ExecuteWhenFinished` 当通用帧队列。
